1. A diferença semântica: 'By' vs. 'On'


Não se prenda tanto à preposição; no SQL do BigQuery, usamos PARTITION BY e CLUSTER BY. A diferença no formulário é apenas gramatical, mas o conceito técnico é o que importa:


PARTITION BY (Particionar por): Divide a tabela fisicamente em 'mini-tabelas' baseadas em datas. Quando você filtra por data, o BigQuery descarta as outras partições sem nem olhar para elas.

CLUSTER ON/BY (Agrupar em): Dentro de cada partição, ele ordena os dados. Se você quer 'Order by VendorID', o Clustering já deixa os dados pré-ordenados no disco.



2. Por que a sua lógica (Partition by VendorID) está errada?


Se você tentar particionar por VendorID, o BigQuery vai reclamar ou ser ineficiente por dois motivos:


Cardinalidade: Particionamento funciona melhor com datas ou inteiros com intervalos claros. O VendorID tem pouquíssimos valores (1, 2, 4). Particionar nisso criaria apenas 3 ou 4 partições gigantes, o que não ajuda em nada no 'Pruning' (pular dados).

Limite do BQ: O BigQuery permite no máximo 4.000 partições por tabela. Datas são perfeitas para isso.


3. A Estratégia Vencedora (Senior DE View)

Question 09: Estimated Bytes for SELECT count(*)


Estimated Bytes: 0 B


Reasoning: BigQuery maintains metadata (storage statistics) for all native materialized tables. This metadata includes the total row count for the table. When a query performs a naked SELECT count(*) without any filters, the execution engine retrieves this value directly from the metadata layer instead of scanning the actual data columns. Consequently, the estimated and actual bytes processed are zero.


Key Constraints:


No Filters: This optimization only triggers if there is no WHERE clause. Adding a filter (e.g., WHERE fare_amount = 0) forces BigQuery to scan the specific column to evaluate the condition, resulting in non-zero bytes processed.

External Tables: This behavior typically does not apply to External Tables. Since the files reside in a GCP Bucket (GCS), BigQuery does not have the same level of real-time metadata control. It may need to read the Parquet file footers to determine the row count, which might show as '0 B' in the estimator but will actually consume Slot milliseconds during execution.

3. FAQ Contribution (Para o documento oficial)


Question: Why does a SELECT count(*) query show '0 bytes processed' in BigQuery?


Answer: For native (materialized) tables, BigQuery does not need to scan the actual row data to perform a simple count(*) without filters. Instead, it retrieves the row count directly from the table's metadata, which stores real-time statistics about the table's storage.


Important Notes:


Filters: If a WHERE clause is added, BigQuery must scan the filtered columns, and the cost will no longer be zero.

External Tables: This optimization typically does not apply to External Tables (e.g., data stored in GCS). BigQuery may report 0 bytes in the estimator but will still consume Slot milliseconds as it has to read file footers/headers to calculate the count, since it doesn't own the metadata layer for external files.
