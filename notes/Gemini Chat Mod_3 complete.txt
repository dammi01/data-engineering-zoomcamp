Aqui estão as táticas para economizar no Módulo 3 (BigQuery) sem comprometer o aprendizado:


1. O 'Vício' da Tabela Externa (Role: Data Engineer)


Em vez de importar (ingestão) todos os dados para dentro do BigQuery de imediato, use External Tables.


Como funciona: O dado fica no GCS (Bucket) em Parquet e o BigQuery apenas 'lê' de lá quando necessário.

Vantagem: Você não paga pelo armazenamento no BigQuery (que é mais caro que no GCS) enquanto está apenas testando queries.


2. Otimização de Custo por Query (Role: Professor)


No console do BigQuery, sempre olhe o canto superior direito antes de dar 'Run'. Ele dirá: 'This query will process X MB when run'.


Evite o SELECT *: Em um banco colunar, isso é o maior erro de iniciante. Selecione apenas as colunas necessárias.

Use Particionamento: Se você filtrar por data em uma tabela de 10GB particionada por dia, o BigQuery lerá apenas os MB relativos àquele dia. O custo cai drasticamente.


3. Terraform como Seguro (Role: Software Engineer)


Não crie recursos 'zumbis'.


Mantenha seu terraform destroy engatilhado para qualquer recurso que cobre por tempo (como instâncias de computação, se usar).

Para o BigQuery e GCS, o custo é por armazenamento/consulta, então o risco é menor, mas manter o código limpo no Terraform evita que você esqueça datasets gigantes ativos.

Quando você escreve apenas a query da External Table, o BigQuery olha para o arquivo no GCS. Como ele ainda não 'leu' o arquivo para saber o tamanho, ele muitas vezes não consegue estimar o custo antes da execução, ou mostra 0 porque ele ainda não mapeou os metadados internos.

Question 09: Estimated Bytes for SELECT count(*)


Estimated Bytes: 0 B


Reasoning: BigQuery maintains metadata (storage statistics) for all native materialized tables. This metadata includes the total row count for the table. When a query performs a naked SELECT count(*) without any filters, the execution engine retrieves this value directly from the metadata layer instead of scanning the actual data columns. Key Constraints:


No Filters: This optimization only triggers if there is no WHERE clause. Adding a filter (e.g., WHERE fare_amount = 0) forces BigQuery to scan the specific column to evaluate the condition, resulting in non-zero bytes processed.

External Tables: This behavior typically does not apply to External Tables. Since the files reside in a GCP Bucket (GCS), BigQuery does not have the same level of real-time metadata control. Question: Why does a SELECT count(*) query show '0 bytes processed' in BigQuery?


Answer: For native (materialized) tables, BigQuery does not need to scan the actual row data to perform a simple count(*) without filters. Instead, it retrieves the row count directly from the table's metadata, which stores real-time statistics about the table's storage.

External Tables: This optimization typically does not apply to External Tables (e.g., data stored in GCS). Calma, não é a Lei de Murphy, é apenas o comportamento padrão de segurança do BigQuery. O erro resourceInUse aconteceu porque você tem tabelas dentro do dataset e o Terraform, por segurança, se recusa a deletar um dataset que não esteja vazio, a menos que você dê uma ordem explícita.


O Diagnóstico


No seu plano de destruição anterior, o atributo delete_contents_on_destroy estava como false. Isso significa que o Terraform tenta deletar o 'container' (dataset), mas o Google bloqueia a ação para evitar que você apague dados acidentalmente.


A Solução (Rápida e Direta)


Você tem dois caminhos. O primeiro é o mais 'ENTJ': resolva pelo console e siga em frente.


Opção 1: Pelo Console (Mais rápido agora)


Vá ao console do BigQuery.

Selecione o dataset trips_data_all.

Clique em Delete.

Digite delete confirmation (ou o que ele pedir) e confirme. Isso apagará todas as tabelas (particionadas, materializadas e externas) de uma vez.

Volte ao terminal e rode o terraform destroy de novo para ele limpar o estado.


Opção 2: Pelo Terraform (O jeito 'correto') Se quiser que o código resolva, você precisa alterar o seu arquivo .tf:


No bloco do google_bigquery_dataset, mude: delete_contents_on_destroy = true

Salve o arquivo.

Rode:
terraform apply -auto-approve
terraform destroy -auto-approve


O que aconteceu com o Bucket?


Note que o google_storage_bucket.demo-bucket foi destruído com sucesso. Isso ocorreu porque no seu log ele estava configurado com force_destroy = true.


Recomendação: Vá pelo Console (Opção 1). É mais rápido para quem já quer encerrar o dia. Delete o dataset manualmente e o trabalho estará feito.
